# A gateway is chosen by a packet, not by a publication

**Status:** Accepted, 2026-09-18. Decided by Milestone 6 ([#56](https://github.com/toon-protocol/TOON_Network/issues/56)) and implemented by [#60](https://github.com/toon-protocol/TOON_Network/issues/60); the shape and the rule are spec §12.1, the glossary terms are **Gateway Handover** and **Gateway Grant**, and the reference gateway carries it in `src/handover.mjs` and `src/admit.mjs`. Follows ADR 0016; the decision of ADR 0013 is untouched.

A tenant chooses a Workload Gateway by **sealing one packet to that gateway's connector**. It does not publish anything, and the gateway does not watch a relay for anything a tenant produced.

Until Milestone 6 the choosing *was* the publishing: a tenant signed a Gateway Grant of kind `30438` naming the gateway in a `p` tag, and the gateway found every grant naming it with one relay filter. ADR 0016 removed that event, because it carried the `workload_id` onto a relay under a tenant's signature and was half of the join that let a third party attribute a deployment. So the channel is gone. What matters is that **the property it bought had to survive its mechanism**: no tenant makes contact with a gateway, registers with it, or holds an account on it. A sealed packet keeps that property. An account would have destroyed it more thoroughly than publishing ever threatened it.

**What publishing bought, and what pays for each afterwards.**

- **Discovery with no account.** A tenant published; the gateway found it. Nobody signed up, and the gateway stored nothing about anybody. This is now paid for by the envelope: a tenant seals one packet to a connector whose sealing key it already has (ADR 0011), and the gateway holds the workload and nothing about the sender. There is still nothing to register for, because there is still nobody to register.
- **Rotation with no operator.** Republishing under the same `d` replaced the grant; a grant naming another gateway withdrew the workload. Renewal is now re-derivation at a later `expires_at` and a second handover, and it replaces what is held for the same reason the republished event did: only the lease's tenant can produce one that works. Withdrawal before expiry needs its own message, the **Gateway Withdrawal** ([#61](https://github.com/toon-protocol/TOON_Network/issues/61)), because a packet nobody sees cannot displace anything by existing.
- **One filter.** A gateway watched a single subscription and was told everything. It now listens on one port instead, and that port is cheaper: no relay to be partitioned from, no replay of an older grant to reason about, no `created_at` to compare.

**What publishing bought that nothing pays for, and why that is right.** A published grant was *verifiable by the gateway alone*: the signature said the tenant meant it, and a gateway could act on an event it had merely read. Nothing replaces that, because nothing can — there is no tenant key any more, which is the whole of ADR 0016.

So authority is established **empirically** instead. Anyone can seal a packet, so a gateway cannot ask *who sent this*; it asks *does this grant work*, by sending `status` to the members the handover names and seeing whether they take it. Being sent something becomes proof precisely because only the holder of the lease's Continuation Token can derive a grant a provider will accept (§6.5.1). The gateway is not weighing the sender. It is asking the only parties that can answer.

That round is **one, immediate and final**. One, because the answer cannot improve by asking again — a grant that does not derive from the lease's token never will. Immediate, because the tenant is present and is waiting to be told whether its workload is being served. Final, because anything a gateway remembers about a handover it did not accept is state a stranger can make it hold: a dropped handover costs one round and then nothing at all.

## Considered Options

- **Keep publishing the grant event.** Rejected upstream, by ADR 0016, and restated here because §12.1 asserted the opposite normatively and a later reader will otherwise re-propose it. A published grant puts the `workload_id` on a relay under a tenant's signature, which is exactly the join across two independently signed events that Milestone 6 exists to remove. Recovering "the gateway can verify it alone" would mean recovering the tenant's signature, and with it everything the signature leaks.
- **Publish a contentless pointer and seal the rest.** Rejected. It keeps a relay in the path for no benefit — the `workload_id` is what a pointer must carry to be a pointer, and that is the field that must not be published. A pointer carrying less than that is not one.
- **Give the gateway an account: registration, an API key, a tenant allowlist.** Rejected, and it is the option that looks most ordinary and costs most. It puts back precisely the identity the rest of the milestone removed, gives the gateway something to be compelled for, and makes the gateway a party the tenant must be known to. "No tenant makes contact, registers or holds an account" is the property the published grant bought, and this option pays for it by giving it up.
- **Trust the packet: serve whatever is sealed to us.** Rejected. Anyone can seal a handover, so this lets a stranger put any workload id on any hostname of any gateway, and lets one take a served workload off by sending a handover naming members that will never answer. The `status` round is what separates a tenant from a stranger, and it costs one free request.
- **Admit lazily: hold the handover and prove it on the first request.** Rejected. A gateway would then hold state for handovers nobody asked about, which is a free hold a burst can fill; a tenant would be told nothing at handover time and would learn its mistake from a browser; and the first request would pay for the proof. Admitting at once means the tenant is told at once, and the gateway holds nothing it has not proven.
- **Rate-limit per sender rather than per member.** Rejected: there is no sender to count. What must be bounded is the load one gateway can be made to put on one provider, and only the member's own bucket bounds that.

## Consequences

- **The amplification ratio is about one to one, and the rate limit is normative.** One sealed packet a stranger paid to deliver buys one free `status` to each member it names. A gateway MUST therefore rate-limit admission per member named and MUST bound how many members one handover may name; otherwise it is a reflector with a public address. Spec §12.1 states both, so an implementer meets them by reading the section rather than by discovering them in production.
- **A gateway cannot allowlist tenants.** There is no tenant identity to put on a list, and this is a consequence of the design rather than a gap: it is the same property that keeps a provider from proving who asked it to run anything. A gateway that wants to serve only certain workloads decides that out of band.
- **A handover carries one grant per member.** `gateway_sub` derives from `continuation(provider)`, which derives under the member's own key, so a single value would admit the gateway at exactly one member while §12.4 asks all of them. This is the one place Milestone 6's per-provider derivation (ADR 0016) shows through into a message shape, and it is load-bearing: it also means a member is never handed another member's grant.
- **A gateway needs no key of its own.** It was a Nostr identity only because a grant named it in a `p` tag and it signed `status` with it. It names nothing and signs nothing now, so what identifies a gateway to a tenant is the connector the handover is sealed to. There is no gateway key to configure, rotate or leak.
- **A gateway reads a relay on a workload's account for two things.** Its members' Provider Profiles and its Takeovers — both downstream of a handover already accepted. A request to a hostname it holds nothing for still reaches no provider and reads no relay.
- **The grant is a secret, on the gateway's side too.** It is what authority the gateway has, so it goes to the members the handover names and nowhere else: never into a log line, an error message or an answer. This is the same rule §6.1.1 puts on a provider, for the same reason.
- **Withdrawal needs a message of its own.** Publishing a grant naming another gateway used to withdraw a workload by existing. Nothing is published now, so a tenant that wants serving to end before `expires_at` sends a Gateway Withdrawal (#61). A withdrawal ends *serving*, not *reading*: the withdrawn gateway keeps a working grant until its moment passes, because there is no revocation before expiry (§6.5.1).
- **Two gateways handed the same workload behave the same.** The canonical hostname is still derived from the workload id and never assigned, and resolution still follows the handover. What two gateways may disagree about is a readable `name`, exactly as before.

# A gateway reaches a member the way its Profile says, and says so when it could not

**Status:** Accepted, 2026-09-22. Decided and implemented by [#114](https://github.com/toon-protocol/TOON_Network/issues/114), found on the live devnet: every Gateway Handover to a connector-fronted provider was accepted and then answered `503 no_running_member`, while the lease was running and the provider answered `status` correctly to anyone who asked it the way the directory says. The rule is spec §12.4; the reference gateway carries it in `src/status.mjs` and `src/profiles.mjs`. Touches ADR 0011 (a Profile pins its connector's sealing key), ADR 0013 and ADR 0017 (what a Workload Gateway is and how it is chosen).

A Workload Gateway asks a Standby Set member for `status` by **sealing the §6.1.2 packet body to that member's `connector_seal_key`, addressing it `<ilp_address>.status`, and posting it to `connector_url`** — the three fields the member's own Provider Profile publishes (§4.1), and nothing else. It derives no URL from any of them.

And a member's answer counts as an answer **about the lease** only when it is a `status` document: one carrying `state` (§6.5) or `error` (§5). Anything else is a fact about the carriage, counted with silence and reported `member_unreachable` (§12.3), never `no_running_member`.

## What went wrong, because it is the argument

The first gateway sent the packet body as plain HTTP to the `status` path *beside* `connector_url` — `…/ilp` with the suffix replaced. The reasoning at the time was recorded in the module and was not silly: `status` is free (§5), so there is no payment to make, and a sealing client would pull a payment library into a process whose whole point is that it holds no key, no channel and no wallet. What it missed is that the invented URL is nowhere in the directory.

A provider's app is **one listener**, and it carries `status`, `availability`, `terminate`, `rotate` **and** every `<listing>.v<n>.spawn` (§5). Which of those a caller may have is decided by the connector in front, from the ILP address the packet is sent to and the claim it carries. Expose that listener at a path on the public internet and every paid route on it is free, so no provider does, and no provider should: the devnet provider answers `POST /status` at its edge with `404` and an empty body. That is correct behaviour, and it was the only behaviour the gateway could not read.

So the bug was not that the carriage was *unusual*; it was that the carriage was **imagined**. The directory says how to reach a member. A gateway that reaches it some other way has an arrangement with nobody.

## The three objections, answered

The module's own note gave three reasons not to seal. Two were already false when it was written and the third is the interesting one.

- *"It would need the connector's self-description."* The Profile carries `ilp_address`. There is no self-description to fetch for that.
- *"It would need the connector's sealing key."* The Profile carries `connector_seal_key`, pinned, which is the whole of ADR 0011 — a tenant seals to that key and to no key a URL told it about.
- *"It would put a payment client into a process whose whole point is that it holds none."* This is the real one, and the answer is that **a free route needs no claim**. `<addr>.status` is priced at `0`; an unpaid packet to a zero-priced route is routed rather than greeted with terms. So the gateway holds a connector client, which is a sealing library that can also pay, and gives it nothing to pay with: an identity generated fresh at startup, written to no store, never funded, holding no channel, with `autoOpenChannel` off. A paid route cannot be bought here even by a bug, which is a stronger guarantee than the old carriage gave — that one merely never *addressed* one.

The key that remains exists because a gift-wrapped packet needs an ephemeral sender, not because anything is bought with it. Nothing on any chain moves on a gateway's account, and a member's books are the same figure after a thousand `status` calls as before the first.

## Considered Options

- **Have the provider expose the free `status` path at its edge.** Rejected, and it was the tempting one: three lines of nginx, `status` is free and token-authenticated, and nothing is "bypassed" by a route that costs nothing. But the path it would expose is not `status`; it is the app's one listener, which also carries `spawn`. The rule the provider's deployment states — only the connector may reach that listener — is the rule that makes "which routes may this caller have" answerable in one place. Carving one exception into it means the next reader has to check, per path, whether the connector is authoritative. And it would have fixed one deployment while leaving the protocol saying nothing about how any other gateway reaches any other member.
- **A new Profile field naming the free-route HTTP base.** Rejected. It publishes a second way in to the same app, which every provider then has to secure separately, and it is a field that exists only because a gateway did not want a sealing library. The directory would be describing a carriage for one party's convenience.
- **Leave the carriage and only fix the reporting.** Rejected as a whole answer, though the reporting fix is real and is kept: a gateway that says `member_unreachable` accurately is still a gateway that cannot serve a workload on any real provider.
- **Let the gateway hold a funded channel and pay whatever a member's connector charges.** Rejected. A gateway's authority is a grant and nothing else (ADR 0017), and a gateway with money is a gateway an operator has to fund, watch and rotate. `status` is free at the member's own edge; a hub that prices its onward hop is a hub the gateway does not go through.

## Consequences

- **A Profile that names only some of the three is dropped.** `connector_url`, `ilp_address` and `connector_seal_key` are one fact — how this member is reached — and a Profile carrying a subset describes a carriage nobody can complete. It is refused where Profiles are read, which leaves the member `member_unreachable`: the honest answer, and never a member that "answered" nothing. Profiles the reference provider publishes have carried all three since §4.1 was written.
- **The gateway goes to the member's own edge, never through a hub.** The member prices its own `status` at `0`; a hub that peers onward may price the same route above zero, and a gateway has nothing to pay it with. This is also what keeps "a gateway calls no paid route" checkable: a member's peer book is unmoved by a resolution.
- **`.anyone` members are unchanged, and now said once.** A member whose `connector_url` is at an `.anyone` host is reached through the configured `socks5h://` proxy and any other member directly (§12.8) — the same rule the forwarding leg has always followed, now applied to the `status` leg at the point where the connector client is built rather than at a socket the gateway owns. A hidden member with no proxy configured is still `no_proxy`, with nothing resolved and nothing dialled.
- **A development sandbox stops needing a shortcut.** The plain carriage forced a sandbox to dial each connector's name at the provider app instead, because the connector was the one thing that would not answer; that came off the honest path as a `GATEWAY_DIAL_REWRITE` entry per provider, including one per hidden provider rendered at bring-up. With the sealed carriage the connector is exactly where its Profile says it is, on the compose network under that name, so those entries are gone and the sandbox reaches a member the way a deployment does.
- **A first `status` to a member costs two extra round trips.** The connector client reads the connector's self-description and the route's price once, and caches both for the life of the client. A gateway that resolves a workload for the first time therefore waits a little longer than one that has asked that member before, which is inside `GATEWAY_RESOLVE_TIMEOUT_MS` and is a fact an operator setting that number should know.
- **The reporting rule stands on its own, and would have been worth making anyway.** A 404 from a hop in front of a provider is not the only way to get an answer that is not a `status`: an HTML error page from a load balancer, a body that is not JSON, an empty 200. Counting any of them as "this member answered, and is not running it" states a fact about the lease that the gateway never learned — the same mistake §12.4 already forbids for a refusal, and a worse one, because the lease was never asked about. A gateway's refusal now names the route, the URL and what came back, so an operator is pointed at the hop rather than at the lease.
- **§12.4 still does not fix a carriage, and should not.** A member and a gateway that have an arrangement of their own may use it; the bytes and the answer are identical. What the spec now says is narrower and is the thing that was missing: the directory describes exactly one carriage, a gateway may not invent a second from a URL the directory gave it for something else, and a member is under no obligation to honour one it was never told about.

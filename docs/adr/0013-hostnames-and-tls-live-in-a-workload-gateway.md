# Hostnames and TLS live in a Workload Gateway, never in the provider

**Status:** Accepted, 2026-09-17. Raised by [issue #15](https://github.com/toon-protocol/TOON_Network/issues/15) from the rig tenant-side design session; accepted by Milestone 5 ([#46](https://github.com/toon-protocol/TOON_Network/issues/46)), which specifies the gateway in spec §12 and the delegation of `status` it needs in §6.5. `rig` builds against it.

**Amended 2026-09-18 (Milestone 6, [#57](https://github.com/toon-protocol/TOON_Network/issues/57)).** The delegation was a published, tenant-signed event of kind `30438`. That kind is gone and the event with it: nothing a tenant produces is published any more, and the delegation is derived from the lease's Continuation Token instead (ADR 0016). The decision this ADR records — that hostnames and TLS live in a Workload Gateway keyed by `workload_id`, never in the provider — is untouched; only the carriage of the authority changed, and the paragraphs below are read with that substitution.

A workload is reachable today only at its provider's `host` and a provider-assigned `host_port`, and a Hidden Provider has no `host` at all (§10). "Push to main and the app is at a stable URL" needs a name that outlives the provider currently running the workload.

We decided that **the provider protocol stays out of hostnames and TLS**, and that the stable name belongs to a **Workload Gateway**: a separate TOON app, reached through its own connector, that fronts a workload by its `workload_id` and resolves that id to whichever provider is running it right now. The provider never owns a domain, never runs ACME, never terminates TLS and never holds a tenant's certificate key. Until a Workload Gateway exists, a tenant that wants HTTPS runs its own reverse proxy inside its workload and publishes `host:port` — which needs no spec change and remains the floor even afterwards.

The decision follows from one property the other options cannot have: **the stable identifier in this protocol is the `workload_id`, not the provider.** A Standby Set shares one tenant-chosen `workload_id` across several providers, and a Takeover moves the workload to a different provider with a different host and a different assigned port, with no tenant online to help (ADR 0010). Any naming layer owned by a provider therefore names something that can move out from under it. A naming layer keyed by `workload_id` names the thing the tenant actually bought.

## Considered Options

- **1. Provider-issued subdomain** (`<workload_id>.<provider-domain>`, provider runs wildcard DNS and ACME and terminates TLS). Rejected on three counts. It is impossible for a Hidden Provider, which publishes no hostname and whose leases are reachable only at `.anyone` addresses (ADR 0008), so it would split the marketplace into workloads that can be hosted and workloads that cannot. It requires every provider to own a domain and operate DNS-01 ACME renewals, which raises the bar for joining a marketplace that deliberately needs nobody's approval to join (ADR 0005) and pushes the provider back into the Kubernetes hostname-operator role the fork dropped (ADR 0001). And the URL still is not stable: it dies at the next Takeover, because the provider in the name is the part that changed.
- **2. Tenant-supplied hostname and certificate in the spawn.** Rejected. It is dominated by option 4: the tenant must own the domain and run ACME either way, and option 2 adds handing the domain's private key to the provider. Worse, ADR 0010 means the key goes to *every* provider in the Standby Set, chosen for price rather than trust, and a key that can impersonate the tenant's domain anywhere is a larger blast radius than the lease-scoped secrets already in `env`. It also does not fit the lease model: certificates rotate every 60–90 days while a spawn is a one-shot request with no route for replacing its content (§5), so each renewal would mean a respawn.
- **3. Workload Gateway.** Chosen. It is the only option that survives a Takeover, the only one that can put a Hidden Provider's workload on a public URL, and it costs the provider protocol nothing: a gateway is an ordinary TOON app built on routes that already exist. It adds a party, and a gateway that terminates TLS reads the traffic it fronts — but that is one party the tenant chooses or runs itself, instead of every provider the tenant happened to buy standby capacity from.
- **4. None.** Kept as the interim and the permanent floor, not as the answer. It needs no spec change and leaves the tenant's key inside the tenant's own container, so rig can ship on it today. It cannot give a Hidden Provider's workload a browser-reachable name at all, and the tenant must re-point DNS itself on every Takeover and respawn — which requires the tenant to be online exactly when ADR 0010 promises it need not be.

## Consequences

- **Gateway interface.** A Workload Gateway serves a hostname derived from the `workload_id`, terminates TLS for its own domain, and forwards to the workload's HTTP port. It learns where to forward by calling the provider's free `status` route (§6.5), and it learns that the provider changed by watching `K_TAKEOVER` events for that `workload_id` (§7.1). Reaching a Hidden Provider's lease means dialling a per-lease `.anyone` address, so a gateway needs `anon` client access.

  **Normative, 2026-09-17 (#46).** All of it is now spec §12, and two details there are sharper than this bullet was. The hostname is `<canonical label>.<gateway domain>`, where the label is the lowercase unpadded base32 of the workload id and not its hex (§12.2): 52 characters, because DNS allows 63 and hex would need 64. And a gateway asks **every** member of the Standby Set at once rather than the provider it last used (§12.4), because a Takeover is exactly the case where the member it last used no longer has the workload.
- **Tension with ADR 0005, to be resolved by the gateway spec.** `.status` requires the lease's tenant signature, and a gateway is not the tenant. So a Workload Gateway cannot re-resolve a workload after a Takeover without some delegated authority that v1 does not define. That gap — delegation, pre-signed rolling status requests, or a new authority carried in the spawn — is the first thing a gateway spec must close, and it is where ADR 0005 will come under pressure. It is a gap, not a contradiction: nothing here lets a provider infer tenant identity from anything but a signed request.

  **Closed, 2026-09-17 (TOON_Network#47).** The delegation is the **Gateway Grant** (spec §6.5): a grant that admits one Workload Gateway to one workload's `status` until it expires, and to nothing else. The gateway presents it on `status` and the provider admits it exactly when the grant applies; any defect is `bad_grant`. ADR 0005 is untouched — the grant is verified out of the request, with no relay read and nothing stored per gateway — and the "which port is the HTTP one?" gap below is closed by the grant's `http_port`.

  The grant is the **authority mechanism this ADR left open**, and of the three doors named above — delegation, pre-signed rolling status requests, or a new authority carried in the spawn — it is the first. A tenant delegates one thing, to one gateway; nothing is pre-signed per request and the spawn gains no field. Its whole price is that **revocation is by expiry**. A provider checks only the grant it is handed, so a tenant that wants a gateway cut off before the grant runs out waits for it to expire. Tenants should therefore choose short expiries and renew.

  **Amended 2026-09-18 (#57).** Milestone 5 carried the grant as a tenant-signed, published event of kind `30438`, addressable on the workload id, so renewal and rotation were the act of publishing it again. Milestone 6 derives it from the lease's Continuation Token and hands it to the gateway out of band instead (ADR 0016): the `workload_id` leaves every relay, nothing tenant-signed is published anywhere, and renewal is re-derivation rather than republication. Everything else in this bullet holds, revocation-by-expiry included.
- **No new spawn or Listing fields.** Because the gateway lives outside the provider protocol, neither §4.2 nor §6.2 gains a field for this — and none was needed in the end. The one thing a gateway had to be told, which of a spawn's `ports` is the HTTP one, is carried by the tenant's own grant (`http_port`, spec §6.5) rather than by the spawn, so the field landed on the delegation and not on the request the provider reads.
- **Consistent with ADR 0008.** A gateway reaching a lease over `.anyone` is an ordinary client of that address and reveals nothing the tenant's own traffic would not. A Hidden Provider stays hidden; its tenant's *workload* stops being hidden, which is the tenant's choice to make.
- **Centralisation risk, deliberately unpriced.** One popular gateway would become a chokepoint and a traffic observer. The mitigation is that a gateway is cheap to run and the tenant picks it; v1 records the risk rather than designing around it.

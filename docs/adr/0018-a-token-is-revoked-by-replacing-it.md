# A token is revoked by replacing it

**Status:** Accepted, 2026-09-22. Decided by Milestone 7 ([#69](https://github.com/toon-protocol/TOON_Network/issues/69)) and implemented by [#70](https://github.com/toon-protocol/TOON_Network/issues/70); the route and its rules are spec §6.8, the glossary term is **Rotation**, and the reference provider carries it in `src/provider/lifecycle.rs` (`rotate`). The tenant's side — a fresh root secret, one rotate per member of the Standby Set, the lease file keeping both roots until every member confirms — is the handover tool's `rotate` (`tools/grant/rotate.mjs`, [#75](https://github.com/toon-protocol/TOON_Network/issues/75)). Follows ADR 0016, which [#75](https://github.com/toon-protocol/TOON_Network/issues/75) amends in place to point here, as it does ADRs 0013 and 0017.

A tenant revokes a lease's Continuation Token by **replacing it**. The free, authenticated route `<addr>.rotate` presents the current token and names the `next` one; the provider stores `next` in its place, persists the lease, and answers. From that moment the old token is `not_tenant` and every Gateway Grant derived from it is `bad_grant`. The provider keeps no list of anything it no longer accepts.

ADR 0016 left a gap and said so: *"There is no rotation before expiry yet; a tenant that needs one respawns."* The Gateway Grant then inherited the gap. A grant is derived from the token, so while the token could not change, nothing derived from it could be cut off early. A tenant whose token leaked had to give up its lease. A tenant that had withdrawn a gateway could stop it *serving* but not *reading* until the grant's moment passed (§12.7). Rotation closes both, and it adds no state to close them.

**Why replacement is enough.** A provider already recomputes a grant from the one token it stores (§6.5.1). Change that one value and every grant anybody holds stops matching, all at once. The provider needs no index of them, because it never held one. The old token dies in the same comparison: it is simply no longer the stored value. Revocation is a side effect of the provider storing exactly one thing.

## Considered Options

- **A revocation list: keep the token, refuse named grants or gateways.** Rejected. To refuse one grant the provider must remember it, or remember the gateway it was handed to. That is per-gateway state the provider must persist, bound and expire, and it is the very state §6.5.1's design removed: a provider "stores no second value, keeps nothing per gateway". It would also break the property that makes a grant cheap to check, which is that the provider can recompute any grant from one stored value. And it would buy selectivity nobody needs. A lease delegates reading to **one** gateway at a time (§6.5.1), so "cut off this gateway but not that one" has no case to serve.
- **Let a grant rotate on its own: a per-lease epoch or salt in the grant derivation.** Rejected. A grant is a pure function of the token and a moment, and that is why the provider can check one without remembering it. To retire one grant but not the token, the derivation would need a second input the provider stores and the tenant can advance, such as a counter. That counter is a second stored value that changes on a tenant's request, which is the same thing as a second token, but with a weaker name and a route of its own. It would also leave the leaked-token case unsolved. Re-deriving at a new `expires_at` already renews a grant (§6.5.1), and it cannot revoke the old one, because both derive from the same token. Only changing the token ends them. So a grant has no rotation of its own, and a grant presented on `rotate` is refused. Only the lease's own token can rotate it, and a gateway can never take a lease from its tenant.
- **A grace period: accept the old token, or grants of it, for a while after rotating.** Rejected. A grace period means the provider stores the old value and a moment at which to forget it, which is the second value this design refuses to keep. It also defeats the main reason to rotate. A tenant usually rotates because it believes a token has leaked, and a grace period is then a window granted to the attacker. The tenant needs no window of its own. It chooses the moment it rotates, it holds both root secrets until every member has confirmed (§6.8), and it hands its gateway grants of the new token through the ordinary admission round, which replaces what the gateway holds.
- **The provider mints the new token.** Rejected. The response would then have to carry a secret, and it would be the first answer in the protocol that does. The token would also stop being something the tenant derives from a root it holds. The tenant names `next`, and the answer is `{ workload_id, rotated: true }` with no token in it.
- **Announce a rotation on a relay.** Rejected. A published rotation would put the `workload_id` back on a relay, which ADR 0016 took it off, and no party needs to learn of it. The provider learns by being asked, and a gateway learns by being refused `bad_grant`.

## Consequences

- **The old root secret is retired too, if the tenant wants it to be.** The provider cannot tell how `next` was made and does not check. The spec therefore *recommends* rather than requires that a tenant mint a fresh root secret for each rotation and derive `next` from it (§6.8). Following that is the tenant tooling's job.
- **A Standby Set is rotated member by member**, with one request per member, as every request already is. A set rotated at some members and not others is a valid state, and a member the tenant cannot reach does not block the rest.
- **A lost answer is recovered by reading, not by retrying.** A replay is `stale_request`, and the old token after a successful rotation is `not_tenant`. So a tenant that did not see the answer sends `status` with `next`, and acceptance means the rotation took effect.
- **The lease is persisted before the answer.** Otherwise a crash straight after a rotation would bring the old token back, and the tenant would believe it was revoked when it was not.
- **Ending every grant at once is the only granularity.** Rotating cuts off the gateway, the leaked token and anything else derived from the old token together. A tenant that wants to keep its gateway re-derives grants from the new token and hands them over again.
- **No new error codes.** Every refusal the route gives is one §5 already had.

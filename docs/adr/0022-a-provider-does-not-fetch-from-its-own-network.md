# A provider does not fetch an image from its own network

**Status:** Accepted, 2026-09-22. Decided and implemented by [#105](https://github.com/toon-protocol/TOON_Network/issues/105), found by CodeQL (`rust/request-forgery`) while reviewing the Milestone 7 PRs and pre-existing on `main`; amended by [#107](https://github.com/toon-protocol/TOON_Network/issues/107), which brought the `relay` hint of a spawn's `registry_entry` under the same rule. The rule is spec §8.4; the reference provider carries it in `src/outbound_guard.rs`, applied in `src/provider/oci.rs`, in the client `src/outbound_proxy.rs` builds and — for the relay hint — in `src/directory.rs`'s `fetch_addressable`, and an operator's exemptions are `image_policy.exempt_registries` for a registry and their own `relay_set` for a relay. Touches ADR 0006 (where a blob's bytes come from) and ADR 0008 (a Hidden Provider's own outbound).

A provider goes to addresses that are **publicly routable** on a tenant's behalf, and to nowhere else. Every outbound host a tenant's image can name is checked — the registry a `reference` or an entry's `oci` source names, the token endpoint that registry's `401` sends the provider to, every redirect, and the `relay` a `registry_entry` hints at — and the check is made on the address that is dialled.

The reason is that the tenant chooses the host. `image.reference` is `<registry>/<repository>`, the provider dials `https://<registry>/v2/…`, and a registry is a host on the internet, not a value the provider owns. So the tenant writes `127.0.0.1:9944/x/y`, or `169.254.169.254/x/y`, or a name of its own that resolves to `10.0.0.5`, and the provider makes requests inside its operator's network on the tenant's behalf. `availability` (§6.4) resolves an image and is free and unsigned, so this costs an attacker nothing and leaves no payment trail. A hostile registry widens it without needing the reference at all: the realm in a `WWW-Authenticate` is a URL that registry chooses and the provider fetches, and so is a `Location`.

**The check is on the address, and it is the address dialled.** A name is whatever its owner's DNS says it is, and it may say something different the second time it is asked. Checking a name and then connecting by that name is not a check: the answer that passed and the answer that is dialled can differ (DNS rebinding). So a provider resolves once and connects to what it checked. The reference provider does this by making the guard the fetching client's own DNS resolver: the resolver returns only the addresses that passed, the client connects to one of those, and nothing looks the name up a second time. A host written as an address literal never reaches a resolver, so those are refused before the request is built.

**A refusal names the source, not the address.** The chain in §8.4 records why each source failed, and a tenant reads that in `refused_image`. What a name resolves to inside a provider's network is exactly what an attacker is asking for, so the message says `oci <registry>/<repository>` and stops there. The refusal fails that source only: another source for the same blob is still tried, as for any other failure.

## Considered Options

- **A deny list of hosts.** Rejected. It is the wrong way round, and it cannot be finished. `image_policy` already carries deny lists for digests and references, and a deny list is fine for "which images will I run" — a question about a public namespace where the operator can name what they object to. "Which addresses may I dial" is a question about the operator's own network, which the operator knows but cannot enumerate: every service they will ever run on it, every address their cloud gives to a metadata endpoint, every neighbour on the same subnet. A rule about routability needs nothing listed and does not go stale.
- **An allowlist of registries.** Rejected as the rule, though the ticket that opened this considered it. An allowlist is a policy about *whom to trust*, not about *where packets go*, and making it the security boundary would break what §6.2's `reference` form is for: a tenant naming any public registry it likes. It would also be a list every operator has to maintain to stay useful, and the operator who does not maintain it either runs nothing or turns it off. The exemption list below is an allowlist, but it is narrow, inverted, and empty by default: it names the addresses an operator is willing to have dialled inside their own network, not the registries a tenant may name.
- **Refuse at connect time rather than at resolve time.** Not chosen, though it is sound: the connector sees the real address and can drop the connection. It answers later, after the socket is opened for a name that resolved outward and then inward, and it gives a worse error — the refusal arrives as a transport failure, with nothing left of which source or which rule. Resolving once and returning only the addresses that passed refuses earlier and keeps the reason.
- **Check the name against a list of names (`localhost`, `metadata.google.internal`, …).** Rejected. Any name resolves anywhere, and the attacker owns the name.
- **Nothing: treat it as the operator's firewall problem.** Rejected. A provider is *built* to fetch from hosts strangers name; an egress firewall that knows which of those is legitimate is a firewall that has to be taught this protocol. The provider is the party that knows which hosts came from a tenant, so the provider is the party that can refuse them.

## Consequences

- **An operator whose registry is internal opts back in.** `image_policy.exempt_registries` is a list of hosts, `host:port`s and CIDRs, **empty by default**, refused at load if an entry does not parse. It is operator configuration; no tenant can reach it, and it is the only way an address inside the operator's network is fetched from. The URLs the operator has already configured — the store `gateway_url_pattern`, the `registry_url_override` escape hatch — are exempt without being listed, because they are the operator's own and are not tenant values.
- **An exempt host is exempt by name.** An operator naming `registry.internal` gets that name wherever it resolves. That is the operator's own registry named in the operator's own config file; the party whose reach into their own network is not a vulnerability is the operator.
- **A token realm must be `https`.** The answer to it is a credential the provider then presents, and the request names the repository being pulled. An exempt host is exempt from this too: an internal registry commonly speaks plain http, and the operator has already said that host is theirs.
- **Redirects are capped.** A registry legitimately redirects a blob pull to its storage backend; nothing real needs five hops, and each hop is a fresh host to check.
- **A Hidden Provider checks address literals only.** Its fetches leave through `anon` as `socks5h`, which means the proxy resolves every name and the provider must never resolve one itself (ADR 0008): a lookup here would undo the hiding. Nothing is lost that matters — an exit relay's private ranges are not the operator's network, and no exit can reach inside it — and the literal case, which is the one a tenant writes directly, is still refused.
- **The rule covers the `relay` hint too** (#107). A spawn's `registry_entry.relay` is a tenant value the provider dials as a websocket to read the entry (§6.2) — the same exposure over a different transport, equally free on `availability` — so it gets the same rule: `ws` or `wss` only, refused unless the address it reaches is publicly routable, refused by naming the hint and never the address, failing that source while the chain carries on. Other outbound URLs a provider has are the operator's own and stay outside this: the directory publisher's `publish_url`, the store `gateway_url_pattern`, the settlement RPC (§10), and the relays of the provider's own Relay Set.
- **A relay hint is checked, not resolved-once-and-dialled, and that is weaker.** The websocket is the nostr client's, which resolves the name inside its own connect and hands the addresses to nobody; there is no resolver seam to be, as there is for the fetching HTTP client. So the name is resolved before `add_relay` and refused there, which leaves a window: the lookup that checks and the lookup that dials are two lookups, and a name whose owner answers them differently is dialled on the second answer. Two things narrow it as far as a check can, and both are normative in §8.4. EVERY address a name answers with must pass, not merely one, because the dialler tries them all (RFC 8305). And a name that does not resolve at all is refused rather than dialled, because a resolver that answers SERVFAIL once and the truth once would otherwise be a bypass that needs no race to win. Closing the window entirely means dialling the checked address ourselves and handing the nostr client a socket, which that client does not accept; it stays open, and is worth revisiting if it ever does.
- **A provider's own Relay Set is the way back in, and needs no new config key.** A relay hint is exempt when it matches a relay in the provider's own `relay_set`, by authority — host and port — the way #105 exempts `gateway_url_pattern`. That is what makes the sandbox's `ws://relay:7100` on a compose network work, and it is the right shape for the same reason: the provider already dials that relay every cadence, so a tenant naming it asks for nothing new, while the rest of that host's ports stay refused. An operator whose relay is internal has already written it down in `relay_set`; `image_policy.exempt_registries` is left meaning registries.
